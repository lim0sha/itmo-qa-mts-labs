# Домашняя работа: метрики и тест-стратегия релиза

Выдаётся **10 ноября 2026**, срок сдачи — **24 ноября 2026** (через две недели). Ориентир по времени: 2–3 часа. Работа индивидуальная. Достаточно таблицы и текста; писать код не обязательно.

## Ситуация и материалы

Вы готовите релиз сервиса заказов: изменены расчёт скидок, повторная оплата и возвраты. Сервис хранит персональные данные, отправляет уведомления и показывает историю заказов. Повторный платёж и выдача чужого заказа недопустимы. На проверку есть один рабочий день; всё одинаково глубоко проверить нельзя.

- `data/bugs.csv` — самостоятельная мини-выборка из 15 багов.
- `data/release.json` — агрегаты **другого** релиза; не складывайте их с CSV.
- Закрытый баг — только `status=Closed`. Критичный prod-баг — `severity=Critical/Blocker` и `where=prod` среди этих же закрытых.
- Reopened в агрегате — число уникальных багов с хотя бы одним переоткрытием среди заданного закрытого потока. Это учебное определение, а не число событий переоткрытия.
- Automation здесь: автоматизированные кейсы / все кейсы заданного набора. Coverage: требования с кейсами / все требования. Эти определения фиксированы для упражнения.

## Что сделать

1. **Рассчитать мини-выборку.** Укажите ID включённых закрытых багов, числитель и знаменатель локального `DCE = 100 × (1 − crit_prod / closed_bugs)`. Отдельно посчитайте долю всех закрытых багов, обнаруженных **до prod**, и объясните, почему это другая величина. Объясните влияние HW-13 и HW-14: почему они не входят в формулу и почему их нельзя игнорировать при решении о релизе.
2. **Рассчитать отдельный релиз.** По JSON определите локальный DCE, плотность (closed/requirements), reopen rate, coverage, actuality и automation. Для каждой величины приведите формулу с подстановкой, единицы и результат. Проценты округлите до двух знаков; плотность — до трёх. Что показывать при нулевом знаменателе? Разберите один такой пример, не подставляя произвольные 0% или 100%.
3. **Интерпретировать.** Сопоставьте DCE/coverage/actuality/automation с учебными ориентирами 98/90/80/75%. Выберите два главных риска и для каждого запишите «наблюдение → возможная причина → как проверить гипотезу → действие». Цифра сама по себе не доказывает причину и не даёт автоматического разрешения на релиз.
4. **Составить мини-стратегию.** Заполните `answer.md`: минимум пять конкретных рисков, вероятность и влияние по шкале 1–3, произведение для приоритета, по одной осмысленной проверке с ожидаемым результатом и уровнем unit/API/UI. Обоснуйте состав проверок на один день, два критерия готовности релиза и оставшиеся риски. Не требуются материалы следующих занятий: достаточно лекции и семинара 10 ноября.
5. **Проверить метрику на Гудхарта.** Для одной выбранной метрики приведите способ улучшить цифру без улучшения продукта и независимую проверку, которая обнаружит такую подмену.

## Формат сдачи

Один ZIP с `answer.md` (или PDF), таблицей расчётов (`.xlsx`, `.csv` или Markdown) и исходными CSV/JSON. Если написали скрипт, приложите его, версию среды и одну команду запуска. Можно использовать предложенный `answer.md`. Отправьте архив в обычный канал сдачи курса, указанный преподавателем. Не включайте внутренние данные компаний и секреты.
